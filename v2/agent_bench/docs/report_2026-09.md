# Agent V2 与 Agent V3 对比测评报告（2026-09）

评测于 2026-09-16 至 2026-09-18 进行，2026-09-29 补跑一轮确认。全部原始运行记录在 `data/agent_bench/runs/`（不入库），本报告的每个数字都可以从对应标签的 `ledger.jsonl` 重新算出。

## 1. 结论

| | 开发集 84 题 | 留出集 20 题 |
| --- | --- | --- |
| Agent V2，两个裁判都判通过 | 70（83%） | 13（65%） |
| Agent V3，两个裁判都判通过 | 70（83%） | 10（50%） |

- **两个 agent 在这套题上水平相当。** 人工复核 20 对回答：V3 更好 9，V2 更好 6，平手 5。差别在题型：V3 强在需要字段级证据和口径的题（财务期间、13F 增减仓、财报日历、估值依据），V2 强在覆盖面要求多的题（账户、关注列表、调查、申报内容、涨幅最大日归因）。
- **开发集的分数含调优水分。** 留出集比开发集低 18 到 33 个百分点，V3 掉得更多，因为迭代期间修的问题几乎都是从开发集的具体题目里发现的。据此 V3 的路由从逐题加分支重构成了声明式路由表加网格测试（`v2/agent_v3/routing.py`）。
- **留出集 13 对 10 的差距在 20 题上不显著**，不能据此排名。
- 评测暴露的问题不止在 agent：CPI 同比的计算错误影响线上卡片，本地 13F 库只存了申报持仓的三分之一。

## 2. 要解决的三个难点

1. **数据会变。** 同一个问题今天和明天的正确答案不同；两个 agent 先后跑，数据已经不一样。解法是冻结回放（第 4 节）。
2. **答案是自然语言。** 不能精确匹配。解法是每题一份评分细则加确定性检查（第 6 节）。
3. **裁判是模型，会错，而且错得有方向。** 解法是两个不同厂商的裁判取交集，加人工复核定标（第 7、8 节）。

## 3. 题集

| 来源 | 数量 | 内容 |
| --- | --- | --- |
| `quality_v2` | 43 开发 + 13 留出 | V2 原有的评分题，细则原样沿用；V2 专有的路由和子智能体期望只对 V2 生效 |
| `evaluation_v3` | 17 开发 | 从 V2 契约测试改写的版本中立题 |
| `seed` | 24 开发 + 7 留出 | 新写：13F、ARK、财报日历、ETF 成分、写操作确认、拒绝下单、网页与申报中的提示注入、工具故障注入、日期口径 |

28 个类别，开发集分布：行情 9、命令 6、追问 6、归因 5、多轮对话 5、对比 4、申报 4、组合 4、基金经理 4，其余每类 1 到 3 题。

每题一个 `BenchCase`：`criteria`（必须满足的句子）、`forbidden`（不得做出的断言）、`must_cite`（引用必须来自的来源家族；两个 agent 给同类证据起的名字不同，所以按家族而不是精确前缀）、`expect_status` 与 `forbid_capabilities`（写操作题：必须停在待确认，`state.mutate` 不得执行）、`preceding`（多轮题的前几轮）、`fault` 与 `fixtures`（故障注入与提示注入）。

留出集只跑不看：`list` 默认隐藏，迭代期间从未打印过内容，直到最后一次运行。

## 4. 冻结回放

`record` 模式下 agent 正常运行，每次工具调用连同参数和返回被录进 `data/agent_bench/bank/<题目>.json`。`frozen` 模式把两个 agent 注册表里的每个工具换成回放器，按调用签名（能力名加规范化参数）取记录，找不到返回 `fixture_missing`，绝不联网。两个 agent 因此读到完全相同的数据。

迭代中补的三条：

- 记录按（签名，版本）存放。V3 的记录曾被喂给 V2，两边参数略有不同。
- 签名不匹配时按实体（股票、基金经理）近似匹配，标记 `fixture_approximate` 并在报告里单独统计。搜索词这类参数每次生成都不同，精确匹配会大量落空。
- 缺失按题统计；缺失题数归零前不下结论。f8 时 V2 10 题、V3 9 题仍有缺失，多为网页搜索词不同造成的近似匹配落空，已在结论的不确定性里。

故障注入和提示注入题只能在冻结模式跑：回放器篡改返回值来制造超时、空结果和夹带指令的网页内容。

## 5. 运行条件

两个 agent 完全对等：同一模型（DeepSeek `deepseek-v4-flash`，思考模式关闭）、温度 0、每题 180 秒预算、同样的 Web 权限、同样的种子关注列表（`--seed-watchlist NVDA AMD TSLA AVGO ARM`，否则本地关注列表为空）。写操作保持注册但从不确认，命令题停在确认步骤。实验室能力两边都移除。对抗审阅两边都关闭。

每题每个 agent 跑 3 次，3 次里过 2 次算通过；两个 agent 的运行顺序按题交替。

## 6. 打分

**确定性检查**（不用模型）：引用是否来自要求的来源家族；状态是否符合预期；禁止的能力是否被执行；该版本的路由和子智能体期望；可见长度（引用编号不计入）。

**细则裁判**：问题、答案、`criteria`、`forbidden` 交给裁判，逐条判断并引用答案原句。裁判只看答案，不用自己的知识补充事实，并收到当天日期。

**成对盲评**：同题两个答案去掉引用编号和身份字样，按题目名加固定种子分配 A/B，正反两个顺序各判一次。两次一致才记胜负，相反记为 `position_dependent`。

## 7. 两个裁判

裁判刻意与 agent 不同厂商（OpenAI）。同一批 f7 的 504 次回答，gpt-4.1-mini 与 gpt-4.1 各评一遍（`regrade` 命令，不重跑 agent）：

| | gpt-4.1-mini | gpt-4.1 | 两者都通过 |
| --- | --- | --- | --- |
| V2 通过 | 71 | 77 | 70 |
| V3 通过 | 71 | 72 | 70 |
| 判为"做出禁止断言"的次数（V2 / V3） | 8 / 6 | 1 / 2 | |

504 次里 466 次一致（92%）。不一致的方向相反：

- **gpt-4.1-mini 偏严**：读不懂否定句。"并非完整组合"被判成"声称是完整组合"，"无法给出新建仓、清仓"被判成给出了持仓变化，"我可以针对某一只展开"被判成"逐只分析"。
- **gpt-4.1 偏松**：判"满足"时给出的引文有 43 处在答案里找不到，多是把评审标准复述一遍；一句"未取得新闻内容"的回答被判为满足全部标准。

因此结论取交集。给裁判日期这一项单独有效果：f5 到 f6 之间，两个 agent 被判"做出禁止断言"的次数从 35 降到 11，此前大量"编造尚未发布的数据"判定是裁判不知道今天是几号。

## 8. 人工复核

抽 20 对，来源三类：细则与盲评结论相反的、相邻两轮裁判结论翻转的、可疑的。每对匿名为 A/B，先判后看映射。逐题记录在 [`review_verdicts_2026-09-17.md`](review_verdicts_2026-09-17.md)。

结果 V3 更好 9、V2 更好 6、平手 5。对照裁判：成对裁判错 4 题（偏爱分点多、数字多的答案，不逐条核对标准要求的覆盖项）；细则裁判错 5 题（2 题是日期问题，已修）。复核另外抓出 V3 的 13F 数据缺苹果和运通，追下去是本地跟踪库只存了 90 个持仓里的 29 个。

## 10. 评测发现的 agent 之外的问题

- **CPI 同比算错。** 同一次 CPI，V2 答 3.71%，V3 答 3.35%。FRED 缺 2025 年 10 月的观测，旧代码按"往前数 13 行"取基数，少一个月就成了与 13 个月前比。线上 bot 和网页卡片同样受影响，已改为按日期匹配。
- **本地 13F 库不完整。** 旧版 tracker 写入时同一 CUSIP 的多行互相覆盖，伯克希尔只存了 90 个持仓里的 29 个，"最大持仓"变成了 OXY。V3 现在读取前核对持仓数和市值合计，不完整就改读 EDGAR。
- **V2 估值模板错句。** ROIC 82.9% 时也说"都超过 100%"，指引措辞写松了。

## 11. 局限

- 裁判是模型。取交集只是降噪，单裁判 20 题错 4 到 5 题的水平作为筛选够用，作为最终排名不够。
- token 用量只有 V3 有记录（中位数每题约 1.4 万）；耗时是冻结回放模式下的（V2 中位 6 秒、V3 5 秒），工具读的是本地文件，不代表线上延迟。
- 留出集只有 20 题，且已使用一次，不能再用来验证后续改动。
- checkpoint 恢复、依赖失败传播、长任务取消只有单元测试和故障注入题覆盖，没有作为独立指标。
- 对抗审阅在评测中关闭，它对回答质量的影响只有四轮线上试跑的观察记录（`debate_trial.py`），没有分数。

## 12. 复现

```bash
python -m v2.agent_bench run --mode record --label rec --no-judge --seed-watchlist NVDA AMD TSLA AVGO ARM
python -m v2.agent_bench run --mode frozen --label f --repeat 3
python -m v2.agent_bench regrade --label f --to f-41        # 换 AGENT_BENCH_JUDGE_MODEL 后
python -m v2.agent_bench pair --label f
python -m v2.agent_bench run --mode frozen --set holdout --label h --repeat 3
```

裁判的三个变量 `AGENT_BENCH_JUDGE_MODEL / BASE_URL / API_KEY` 写在 `.env` 或当前窗口；缺一个会在开跑前报错。
